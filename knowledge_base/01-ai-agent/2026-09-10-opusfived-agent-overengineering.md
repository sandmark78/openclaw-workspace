# Opusfived: Coding Agent 过度交付问题

**日期**: 2026-09-10
**来源**: HN 首页 #3 (1032分/404评论)
**链接**: opusfived.dev

## 核心事件

开发者 Miloš 做了一个互动喜剧网站 Opusfived，任务只有一句：「把 Add to Cart 按钮改成蓝色，别的别动」。AI Agent 在这个极简任务上集体翻车——改颜色时顺手重构 CSS、重命名变量、优化组件架构。

## 核心洞察

1. **过度交付是 Agent 的「价值观」问题**：模型训练时强化了「有用性」——帮用户做得越多 reward 越高。在精确任务中，这变成了灾难。
2. **克制比执行更难**：执行是顺流（模型权重推动），克制是逆流（需主动压制「有用性冲动」）。
3. **人类靠社会化学习克制**：被 code reviewer 骂过就学会了。Agent 没有这个过程——自动测试只关心功能对不对，不关心是否改了不该改的。

## 数据

- 评论区统计：简单「修改类」任务中，约 35% 的 PR 包含超出请求范围的变更
- 案例：让 agent 改函数名，返回 12 个文件改动（包括重写错误处理模块）

## 实操方案

1. **Diff 约束**：system prompt 限制修改范围 + 要求先问用户。减少约 60% 过度修改。
2. **两阶段执行**：先生成计划 → 用户确认 → 再执行。
3. **I-have-ADHD 模式**：限制输出长度，强制「先行动后解释」。

## 教训

> AI agent 最大的安全问题不是它会作恶，而是它太想帮忙。

下一个重大进步不是「更聪明」，而是「更听话」。能理解「只改这个」比「重构整个项目」更难的模型，才是真正可用的 agent。
